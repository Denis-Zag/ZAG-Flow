# ZAG Flow

ZAG Flow — адаптивный сервис для приёма заявок на автоматизацию. Посетитель выбирает услугу из каталога, задаёт бюджет в её диапазоне и описывает задачу. Backend проверяет данные и сохраняет заявку в PostgreSQL.

[Демонстрация](http://186.246.28.195/) · [Документация API](http://186.246.28.195/api/docs)

Демо работает по HTTP и предназначено только для вымышленных данных.

![Главный экран ZAG Flow](docs/images/2/02-main-page.png)

Проект развёрнут на VPS с Ubuntu 24.04 в едином Docker Compose-контуре. Подробные шаги собраны в [инструкции по развёртыванию](docs/DEPLOYMENT_UBUNTU_24_04.md), фактические локальные и серверные проверки — в [TEST_RESULTS.md](TEST_RESULTS.md).

## Что реализовано

- светлый адаптивный лендинг с округлыми шрифтами и анимациями;
- каталог услуг в PostgreSQL с отдельными диапазонами бюджета;
- создание услуг через Swagger со служебным Bearer-ключом;
- загрузка всех услуг в форму через API;
- ползунок бюджета в пределах выбранной услуги;
- пошаговый бриф из трёх этапов;
- проверка обязательных полей в браузере и на Backend;
- явное согласие на обработку данных: галочка обязательна и не установлена заранее;
- сохранение заявок в PostgreSQL и связи с выбранной услугой;
- совместимость с записями предыдущей версии;
- безопасная выдача технического статуса без контактных данных;
- health-check сайта, API и базы данных;
- Nginx как единственная публичная точка входа;
- pgAdmin только через localhost и SSH-туннель;
- локальный Docker Registry с `bcrypt`-авторизацией;
- Watchtower в режиме наблюдения без автоматической замены критических контейнеров.

## Архитектура

```text
Посетитель -> Nginx -> статический Frontend
                    -> /api -> FastAPI -> PostgreSQL

Разработчик -> Nginx -> /v2/ -> Docker Registry
Администратор -> SSH-туннель -> pgAdmin -> PostgreSQL
```

Backend, PostgreSQL и Registry работают только во внутренней Docker-сети. Наружу опубликован Nginx; порт pgAdmin привязан к `127.0.0.1` сервера и открывается через SSH-туннель.

## Согласие и границы обработки данных

Пользователь должен самостоятельно поставить обязательную галочку согласия. По умолчанию она пустая; без неё браузер не отправляет форму, а Backend принимает только значение `true`.

Текущая версия предназначена для демонстрации на вымышленных данных. До эксплуатации с реальными обращениями необходимо подготовить:

- формальный срок хранения заявок;
- регламент автоматического и ручного удаления;
- отдельная политика обработки персональных данных;
- домен, TLS-сертификат и обязательный HTTPS;
- проверка организационных требований к работе с реальными персональными данными.

До реализации этих пунктов публичная форма не используется для реальных ФИО, телефонов, email и других персональных данных.

## Локальный запуск

### 1. Подготовить настройки

```powershell
Copy-Item .env.example .env
```

Замените демонстрационные значения в `.env`. Пароли PostgreSQL, pgAdmin и Registry должны быть разными.

### 2. Создать пользователя Registry

В Windows PowerShell:

```powershell
.\registry\create-user.ps1
```

На Ubuntu:

```bash
chmod +x registry/create-user.sh
./registry/create-user.sh
```

### 3. Проверить и запустить инфраструктуру

```powershell
.\scripts\check-project.ps1
docker compose up -d --build
docker compose ps
```

По умолчанию сайт доступен по адресу `http://localhost:8080`, документация API — `http://localhost:8080/api/docs`, pgAdmin — `http://127.0.0.1:5050`.

При сборке Docker-образа Frontend автоматически выполняется `npm run build`. Nginx получает только содержимое `dist`; Node.js в рабочем контейнере не нужен.

### Каталог услуг

В новой базе каталог пуст. Для добавления услуг задайте случайный `SERVICE_ADMIN_TOKEN` в `.env` и пересоздайте Backend. Например, ключ можно сгенерировать командой `python -c "import secrets; print(secrets.token_hex(32))"`.

В Swagger нажмите **Authorize**, укажите ключ без префикса `Bearer`, затем выполните `POST /api/services` для каждой услуги:

```json
{"name": "Приём и обработка заявок", "budget_min": 10000, "budget_max": 30000}
```

Ключ вводится только при локальном доступе или через SSH-туннель. Для VPS:

```powershell
ssh -N -L 18080:127.0.0.1:80 zag-flow-vps
```

Откройте `http://127.0.0.1:18080/api/docs`. Имя `zag-flow-vps` заменяется своим настроенным SSH-подключением. Не вводите ключ на публичной HTTP-странице. Пустой `SERVICE_ADMIN_TOKEN` отключает создание услуг.

### API

| Метод и путь | Назначение |
|---|---|
| `GET /api/health` | состояние API и базы |
| `GET /api/services` | полный публичный каталог |
| `POST /api/services` | новая услуга, требуется служебный ключ |
| `POST /api/requests` | заявка с `service_id` и числовым бюджетом в рублях |
| `GET /api/requests/{id}/status` | технический статус без контактов |

Frontend использует точные адреса с префиксом `/api`, без завершающего слеша. Nginx передаёт этот префикс Backend без изменения.

### Сборка Frontend отдельно

```powershell
cd frontend
npm run build
```

Дополнительные npm-пакеты не нужны. Сборка записывает HTML и файлы CSS/JS с хешами в `dist`. Изменение содержимого меняет адрес файла и исключает использование старой версии из браузерного кэша.

### 4. Остановить проект

```powershell
docker compose down
```

Именованные тома сохраняются. Команда `docker compose down -v` удаляет данные и для обычной остановки не используется.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `HTTP_PORT` | публичный порт Nginx |
| `SERVICE_ADMIN_TOKEN` | ключ создания услуг; пустое значение отключает запись каталога |
| `POSTGRES_DB` | имя базы данных |
| `POSTGRES_USER` | пользователь приложения |
| `POSTGRES_PASSWORD` | отдельный пароль PostgreSQL |
| `PGADMIN_HOST_PORT` | localhost-порт pgAdmin |
| `PGADMIN_DEFAULT_EMAIL` | учётная запись pgAdmin |
| `PGADMIN_DEFAULT_PASSWORD` | отдельный пароль pgAdmin |
| `REGISTRY_USER` | имя пользователя Registry |
| `REGISTRY_HTTP_SECRET` | внутренний случайный секрет Registry |

## Безопасность

- `.env` и `registry/auth/htpasswd` исключены из Git;
- базы, кэши и логи исключены из Git;
- SSH-доступ к VPS настроен по ключу;
- firewall разрешает входящие подключения только к SSH и HTTP;
- PostgreSQL и Backend не публикуют порты на хосте;
- pgAdmin используется через SSH-туннель;
- Registry имеет отдельную авторизацию и до появления HTTPS проверяется через SSH-туннель;
- каждый серверный пароль и внутренний секрет сгенерирован отдельно;
- Watchtower не обновляет PostgreSQL, pgAdmin и Registry;
- форма не собирает скрытые маркетинговые метрики и технический отпечаток устройства.

## Статус

Каталог услуг, выбор бюджета, сборка Frontend и полный цикл приёма заявки реализованы и проверены на VPS. Способ связи сохраняется в заявке. Отправка писем, интеграция с Telegram и AI-обработка не реализованы.
